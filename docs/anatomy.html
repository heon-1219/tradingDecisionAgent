1. 무엇을 만들었나

한 문장: 주소창에 질문을 넣으면 JSON으로 답이 나오는 서버.

평가자는 우리 서버에 이렇게 물어봅니다. 인증도 없고 POST도 없습니다. 주소만 있으면 됩니다. 

# 평가자가 보내는 것
GET /answer?question_id=Q-001&question=현재 판매가능한 원화채권 중 AA- 이상 종목 알려줘

우리 서버는 항상 200 OK와 함께 정확히 5개 필드를 돌려줍니다. 오류가 나도 500을 내지 않습니다.

{
  "question_id": "Q-001",
  "question":    "…요청 그대로…",
  "retrieved_context": "[근거 1] 국내채권마스터(v_bond_kr) · 기준일 2026-08-21 · 78건 …",
  "think_trace":      "1. 사전분석 … 2. 라운드 1: sql_query … 3. final_answer",
  "answer":           "매수 가능한 AA- 이상 원화채권은 78건입니다 …"
}

핵심은 answer 옆에 반드시 근거가 붙는다는 것입니다. 어느 테이블의 며칠자 데이터를 몇 건 봤고, 어떤 SQL을 실행했고, 어떤 상품코드를 참조했는지가 retrieved_context에 그대로 남습니다. 데이터로 확인이 안 되면 지어내지 않고 "제공된 데이터로는 확인할 수 없습니다"라고 답합니다.

왜 그게 중요한가 — 대회 평가 35문항 중 5문항은 답할 수 없는 질문입니다. 거기에 그럴듯한 답을 만들어내면 감점이고, "확인할 수 없음"이라고 해야 정답 처리됩니다. 즉 이 시스템에서 "모른다고 말하는 능력"은 부가 기능이 아니라 채점 항목입니다.

3. 질문 하나가 처리되는 과정

LLM은 답을 "아는" 게 아니라, 도구를 써서 "찾아옵니다".

  1. 사전 분석 — LLM을 부르기 전에

    질문에서 상품명처럼 보이는 부분을 뽑아 실제 상품과 대조하고, 기업·테마·운용사 사전을 매칭하고, "AA-", "위험등급 2등급" 같은 값이 실제로 존재하는 값인지 온톨로지에 물어봅니다.

    # "신용등급 AAAA인 채권 찾아줘" → LLM 호출 전에 이미 결론이 나옵니다
⚠ 온톨로지 위반: 신용등급 'AAAA'는 존재하지 않는 값입니다.
   유효한 신용등급: AAA, AA+, AA0, AA-, A+, … D

  2. LLM이 계획을 세웁니다

    질문과 사전분석 결과를 받은 LLM이 "이건 SQL로 풀 문제", "이건 그래프를 타야 함"을 판단하고 도구를 호출합니다. 우리가 SQL을 미리 짜두는 게 아니라 LLM이 그 자리에서 작성합니다.

  3. 도구가 실행되고 근거가 기록됩니다

    여러 도구를 동시에 실행합니다. 각 결과에는 어느 테이블·며칠자·몇 건·무슨 쿼리였는지가 자동으로 붙어 최종 retrieved_context가 됩니다. 사람이 답을 검증할 수 있게 하는 부분입니다.

  4. 2~3을 반복합니다 (최대 6라운드, 50초)

    결과가 부족하면 조건을 바꿔 다시 찾습니다. 50초 예산이 임박하면 서버가 "지금까지 확보한 근거로 즉시 답하라"고 지시합니다. 대회 권장이 문항당 60초라서 그 안에 반드시 끝나게 설계했습니다.

  5. 답변을 3가지 상태 중 하나로 제출합니다

    answered(근거 있음) · cannot_confirm(데이터로 확인 불가) · clarify(조건이 모호해 되물음). LLM이 규칙을 어기면 서버가 마지막에 교정합니다.

4. 네 개의 저장소, 질문 유형별 경로

같은 데이터를 네 가지 방식으로 색인해 둔 이유가 여기 있습니다.

난이도 상 예시인 "에코프로의 자회사를 편입한 ETF 중 순자산이 큰 상품의 위험요인"은 세 경로를 모두 씁니다: 그래프로 자회사(에코프로비엠·에이치엔·머티리얼즈)를 찾고 → 그걸 편입한 ETF 79개를 찾고 → SQL로 순자산 정렬 → 문서에서 위험요인 설명. SQL만으로는 첫 단계부터 불가능합니다. 제공 데이터에 "편입종목" 컬럼 자체가 없기 때문입니다.

5. 갈림길과 선택

각 단계에서 무엇을 고를 수 있었고, 무엇을 골랐고, 왜 그랬는지.

결정 01

전체 구조를 무엇으로 할까

LLM에게 얼마나 자유를 줄 것인가?

기각NL2SQL 한 방LLM이 SQL 한 줄 쓰고 끝. 가장 빠르고 단순하지만 테마·편입종목·관계 질문을 못 풀고, 답할 수 없는 질문에도 답을 만들어냄.
선택도구를 쓰는 AgentLLM이 상황을 보며 SQL·그래프·검색을 골라 반복 호출. 유연하지만 응답 시간과 비용이 늘어남 → 시간 예산으로 통제.
기각고정 파이프라인질문을 분류해 정해진 템플릿 실행. 시간은 가장 예측 가능하지만 난이도 '상' 문항에서 무너지고 확장이 어려움.

왜 — 평가 문항이 상·중·하 10문항씩 섞여 있고 답변불가 5문항이 포함됩니다. '하' 문항만 보면 NL2SQL이 이기지만, 배점의 3분의 1인 '상' 문항은 여러 저장소를 오가야 풀립니다. 대신 고정 파이프라인의 장점(시간 통제·검증기·강제 종료)은 Agent 안에 규칙으로 넣었습니다.

결정 02

데이터를 어디에 담을까

엑셀 8개 파일을 어떤 형태로 다룰 것인가?

기각엑셀을 매번 읽기준비가 필요 없지만 질문마다 수십 초가 걸리고 필터·정렬을 직접 코딩해야 함.
선택SQLite 파일 1개5.3만 행은 SQLite에 아주 작은 크기. 서버 설치가 필요 없고 파일 하나라 Docker 이미지에 그대로 구워 넣을 수 있음.
기각PostgreSQL기능은 충분하지만 이 데이터 규모에 DB 서버를 따로 띄우는 건 배포·운영 부담만 늘어남.

왜 — 평가 기간(9/7~9/20) 동안 서버가 계속 떠 있어야 합니다. 움직이는 부품이 적을수록 안 죽습니다. SQLite면 컨테이너 하나로 끝납니다.

덤으로 한 일 — 원본 컬럼명(pd_no, crd_grd)은 그대로 두되, 뜻이 분명한 컬럼을 계산해 뷰로 얹었습니다. 예: is_sellable(실제 매수 가능한 채권 634건), fund_family(같은 펀드의 클래스들을 하나로 묶는 키 — 23,676행이 17,795개 펀드로 정리됨), manager_name(운용사 표기 통일).

결정 03

온톨로지를 어떻게 쓸까

제출 필수 항목인데, 제출용으로만 쓸 것인가 실제로 돌릴 것인가?

기각제출용 문서로만TTL 파일을 만들어 내되 코드는 안 씀. 20% 항목은 채우지만 답변 품질에 기여가 0.
기각프롬프트에 붙여넣기온톨로지 내용을 설명으로 LLM에게 전달. 기술세션 자료 기준 개선 폭 +2.4%p에 그침.
선택런타임이 읽어서 실행서버가 켜질 때 TTL을 파싱해 컬럼 설명표와 값 검증기를 자동 생성. 같은 자료 기준 +20%p.

왜 — 주최측 기술세션이 직접 실험 수치를 공개했습니다: "온톨로지는 '설명'이 아니라 '실행'에 — 프롬프트 주입 +2.4%p, 런타임 식별 +20%p". 채점자가 보고 싶어 하는 게 무엇인지 명시된 셈입니다.

실제 효과 — TTL에 신용등급 20단계가 순서대로 정의돼 있어서, "AA- 이상"이라는 말을 ('AAA','AA+','AA0','AA-')로 자동 변환하고, "AAAA"는 존재하지 않는 값이라고 LLM 호출 전에 판정합니다.

결정 04

그래프에 추론을 넣을까

"KODEX 로봇액티브는 국내ETF다"만 저장했을 때, "그건 ETF인가? 금융상품인가?"에 답할 수 있어야 하는가?

기각저장한 것만 답하기구현이 단순하고 빠름. 하지만 ?p a fp:ETF 질의가 0건을 반환 — LLM이 자연스럽게 쓸 법한 질의가 조용히 실패함.
선택규칙으로 사실 늘리기기동 시 상위 클래스 상속·역관계·domain/range를 계산해 저장. 명시 96.9만 + 추론 10.9만 트리플.

왜 — 기술세션 01-4가 통째로 이 주제입니다("공리 + 논리 규칙 = 새로운 사실, 2개를 넣으면 5개가 된다"). 처음엔 이게 빠져 있어서 상위 클래스 질의가 전부 0건이었고, 과제설명서를 다시 읽으며 발견해 채웠습니다. 기동 시간이 늘지만(추론 계산에 약 25초) 실제로 쓰이는 술어만 처리하도록 최적화해 그래프 구축 전체를 150초 → 83초로 줄였습니다.

결정 05

검색을 어떻게 결합할까

이름으로 찾는 검색과 의미로 찾는 검색을 어떻게 섞을 것인가? — 가장 오래 붙든 문제

기각어휘 검색만표기가 정확하면 최고. 하지만 과제설명서가 Vector를 명시적으로 요구했고, 표현이 다른 질문에 약함.
기각벡터 검색만정확한 상품명을 물었을 때 엉뚱한 유사 상품을 1위로 올림. 위험함.
기각RRF 대등 결합교과서적 방법. 실제로 붙여보니 두 검색기가 각각 어중간하게 올린 무관 상품이 1위를 차지하는 사고 발생.
선택어휘 머리 + 벡터 꼬리상위 자리는 어휘 검색이 갖고, 하위 30% 자리를 "벡터만 찾아낸" 상품에 배정. 어휘보다 나빠질 수 없는 구조.

왜 — RRF(Reciprocal Rank Fusion)는 두 검색기가 동의하는 문서를 위로 올립니다. 그런데 "배터리 양극재 관련 상품"을 물었을 때 무관한 재간접 펀드가 양쪽에서 중간 순위에 걸리는 바람에, 어휘 검색이 정확히 찾아낸 BNK 2차전지양극재를 제치고 1위가 됐습니다.

이게 왜 위험한가 — 1위 후보가 틀리면 LLM이 그걸 근거로 답을 씁니다. 검색 순위 오류가 답변 오류로 바로 번집니다. 그래서 "하이브리드가 어휘 검색보다 나빠질 수 없음"을 구조로 보장하는 쪽을 택했습니다.

그래도 벡터가 버는 것 — 영어로 "China semiconductor ETF"를 물으면 어휘 검색은 영문 해외 ETF만 찾지만, 벡터가 꼬리 자리에 KODEX 미국반도체 같은 국내 ETF를 추가로 올려줍니다.

결정 06

벡터를 무엇으로 만들까

임베딩 API를 쓸 것인가, 로컬에서 만들 것인가?

기각상용 임베딩 API품질이 가장 좋지만 평가 기간에 API 키가 하나 더 살아 있어야 하고, 5.3만 건 임베딩 비용·시간이 듦.
기각로컬 임베딩 모델키는 필요 없지만 2GB 모델 다운로드 + CPU 추론으로 기동이 크게 느려지고 이미지가 무거워짐.
선택TF-IDF + LSA (384차원)키 없이 결정적으로 동작하고 기동 시 13초에 만들어짐. 환경변수 한 줄로 상용 임베딩 전환 가능.

왜 — 평가용 API가 2주간 떠 있어야 하는데, 외부 의존성이 하나 늘면 죽을 확률도 늘어납니다. 품질이 부족하면 VECTOR_BACKEND=openai로 코드 수정 없이 바꿀 수 있게 문을 열어뒀습니다.

측정해서 고친 것 — 처음 만든 벡터는 쓸모없었습니다. "배터리 양극재"를 물으면 무관한 ELS 사모펀드가 유사도 0.89로 1위였습니다. 원인은 한글 상품명에 증권투자신탁·사모·파생형 같은 껍데기 단어가 너무 많아 벡터 공간이 그쪽으로 쏠린 것. 자주 나오는 단어를 잘라내자(max_df=0.005) 프로브 7개 중 1개 정답이 6개로 올라갔습니다.

결정 07

외부 데이터를 쓸까

제공 데이터에 없는 "ETF 편입종목"을 직접 수집할 것인가?

기각제공 데이터만 사용가장 안전하고 규칙 위반 위험 0. 하지만 예시 문항 5개 중 2개를 아예 못 풂.
선택편입종목 수집 + 사전 구축국내 ETF 1,162종목의 상위 편입종목을 수집(22,599행). 기업 사전으로 모회사·자회사 관계를 연결.

왜 — 규칙이 외부 수집을 명시적으로 허용하고("금융상품 관련 데이터는 참가팀이 수집해 활용 가능"), 심지어 "기준데이터만 물어보지 않음"이라고 예고했습니다. 예시 문항 "캠브리콘이 편입된 중국반도체 ETF", "에코프로 자회사를 편입한 ETF"는 편입종목 없이는 원천적으로 불가능합니다.

발견 — 네이버금융은 캠브리콘을 "한무기"(寒武纪의 한국식 표기)로 적습니다. 종목코드 688256으로 연결해야 찾아집니다. 기업 사전에 이런 별칭을 넣어둔 이유입니다.

지킨 규칙 — 외부 데이터가 주최측 데이터와 충돌하면 주최측 우선. 프롬프트에 명시했습니다.

결정 08

"모른다"를 어떻게 강제할까

답변불가 5문항에서 감점당하지 않으려면?

기각프롬프트로 부탁하기"모르면 모른다고 하세요"라고 지시. LLM이 자주 어깁니다.
선택상태 3종 + 서버 교정LLM이 답을 낼 때 반드시 상태를 고르게 하고, 사전분석이 "존재하지 않는 값"을 잡았는데 LLM이 답을 지어내면 서버가 확인불가로 되돌림.

왜 — 프롬프트는 부탁이고 코드는 보장입니다. 답변불가 문항은 배점이 걸린 항목이라 부탁에 맡길 수 없습니다.

결정 09

어떤 LLM을 쓸까 — 규정으로 확정됨

주최측 공지: 답변 생성 파이프라인은 NCP HyperCLOVA X 필수.

확정HyperCLOVA X (HCX-005)CLOVA Studio의 OpenAI 호환 엔드포인트로 연결. 규정이 요구하는 구간(의도분석·답변생성)을 전부 담당.
개발용Anthropic / OpenAI코드에는 남겨두되 제출·평가에는 사용 불가. 답변 품질을 비교해볼 때만 씁니다.
해당없음유료 LLM 추가 사용주최측이 유료 LLM 사용 지양 권고. 우리는 답변 경로 외에 다른 LLM을 쓰지 않습니다(벡터도 로컬 계산).

결과적으로 어댑터 구조가 값을 했습니다 — 이전 결정에서 제공자를 갈아끼울 수 있게 분리해뒀기 때문에, 이번 공지 반영은 클래스 하나 추가 + 기본값 변경으로 끝났습니다. 도구 호출 규격이 OpenAI와 동일해서 대화 로직은 그대로 재사용했습니다.

CLOVA에서 주의할 점 두 가지 — ① function calling은 max_tokens가 1024 이상일 때만 동작합니다(미만이면 도구를 아예 호출하지 않아 "모델이 도구를 안 쓴다"처럼 보입니다 — 코드에서 자동으로 올려줍니다). ② function calling은 사고(reasoning)·구조화출력 모드와 동시에 켤 수 없습니다.

설정 — LLM_PROVIDER=clova, LLM_MODEL=HCX-005, CLOVA_API_KEY에 CLOVA Studio 키. 엔드포인트는 https://clovastudio.stream.ntruss.com/v1/openai입니다.

"구매 가능"을 무엇으로 판정할까 — 공지로 뒤집힌 정의

주최측 공지: BUYABLE_QUANTITY 값은 무효, 상장폐지·리스팅 종료 제외 종목은 모두 구매가능으로 가정.

대신 잃은 정보를 살렸습니다 — 매수수익률·세후수익률은 여전히 634건에만 수록돼 있습니다. 그래서 "수익률"을 묻는 질의는 has_buy_yield=1을 함께 걸도록 프롬프트에 명시했습니다. 그러지 않으면 수익률 칸이 전부 비어 있는 표가 나옵니다.

확정됨

LLM은 NCP HyperCLOVA X 필수로 확정됐습니다

공지: "질의에 대한 답변 제작 API 제작 시 NCP Hyper ClovaX 필수. 질의 Intent분석 - (데이터 조회 및 증거 제작) - 답변 생성 이외에는 제약사항 없음." 그리고 "유료버전의 LLM 사용은 지양" 권고도 함께 나왔습니다.

튜닝 여지

응답 시간 기준이 바뀌어 예산을 늘렸습니다

공지: "응답시간의 기준은 공개하지 않으며, 타임아웃 300초는 물리적 '미응답' 처리이므로, 늦게라도 응답(300초 미만)과는 점수 차등 예정." 즉 느려도 맞히는 편이 빠르게 틀리는 것보다 낫습니다.

→ 내부 예산을 50초 → 120초, 도구 라운드를 6 → 8로 올렸습니다. HyperCLOVA X의 실제 응답 속도를 측정한 뒤 다시 조정해야 합니다. 300초에 걸리는 문항이 하나라도 나오면 그건 미응답 처리라 반드시 피해야 합니다.

데이터 한계

없는 데이터가 무엇인지 알고 있어야 합니다

국내ETF 총보수는 18%만 수록돼 있고, 펀드 보수 컬럼은 단위가 공개되지 않았으며(절대값 해석 금지, 클래스 간 상대 비교만), 해외ETF·펀드는 편입종목이 없습니다. 펀드 마스터에는 공모 14,716건 외에 사모 8,960건도 섞여 있습니다.

→ 전부 프롬프트와 온톨로지 주석에 적어뒀고, 값이 없으면 "데이터 없음"이라고 답하게 했습니다. 답변을 검토할 때 이 부분이 제대로 지켜지는지 봐주세요.

기준일

편입종목의 시점이 상품 데이터와 다릅니다

상품 마스터는 2026-08-21 기준인데, 네이버에서 받은 편입종목은 수집일(2026-09-03) 기준이고 네이버가 표시하는 포트폴리오 기준일은 2026-09-01입니다.

→ 섞어서 답할 때 시점이 다르다는 걸 알고 있어야 합니다. 제출 직전에 한 번 다시 수집하면 시점 차이를 줄일 수 있습니다.

제출 형식

저장소 최상위 구조를 맞춰야 합니다

과제설명서가 요구하는 구조는 저장소 루트에 src/, ontology/, requirements.txt, README.md입니다. 지금은 이것들이 fin-agent/ 폴더 안에 있습니다.

→ 주최측 저장소에 올릴 때는 fin-agent/ 폴더가 아니라 그 안의 내용물을 루트에 올려야 합니다. 제출물에는 API 주소와 명세서도 포함해야 합니다.

8. 직접 해보기

순서대로 따라가면 됩니다. 1~3단계는 API 키 없이도 됩니다.

  1. 환경 준비 (한 번만)

    Windows 터미널에서 fin-agent 폴더로 이동한 뒤:

    # 가상환경이 이미 .venv에 있습니다
.venv\Scripts\python.exe -m pip install -r requirements.txt

# 데이터베이스 만들기 (1~2분) — 이미 있으면 건너뛰어도 됩니다
.venv\Scripts\python.exe scripts\build_store.py

    성공 신호: done: {'bond_kr': 21882, ... 'fund_pub': 23676}이 찍히고 data/store/products.db가 생깁니다.

  2. 테스트 돌려보기 — 키 없이 전체 검증

    .venv\Scripts\python.exe -m pytest -q

    성공 신호: 52 passed. 실패가 나오면 그 파일 이름이 어느 부분이 깨졌는지 알려줍니다 (test_build_store=데이터 적재, test_graph=그래프·추론, test_vector=벡터 검색, test_agent=API 계약).

  3. 내부를 직접 들여다보기 — 여기서 감이 잡힙니다

    LLM 없이 각 저장소에 직접 질문을 던지는 도구를 만들어뒀습니다. 이걸 여러 번 돌려보는 게 시스템을 이해하는 가장 빠른 길입니다.

    # 지금 뭐가 실려 있는지 한눈에
.venv\Scripts\python.exe scripts\explore.py health

# SQL 직접 실행 — LLM이 쓰는 것과 같은 뷰
.venv\Scripts\python.exe scripts\explore.py sql "SELECT pd_nm, crd_grd, buy_yield FROM v_bond_kr WHERE is_sellable=1 ORDER BY buy_yield DESC LIMIT 5"

# 검색 3가지 방식 비교 — 결정 05를 눈으로 확인
.venv\Scripts\python.exe scripts\explore.py search "차이나 반도체" --mode lexical
.venv\Scripts\python.exe scripts\explore.py search "차이나 반도체" --mode vector
.venv\Scripts\python.exe scripts\explore.py search "차이나 반도체" --mode hybrid

# 그래프 관계 — 에코프로의 자회사는?
.venv\Scripts\python.exe scripts\explore.py graph "에코프로" --relation hasSubsidiary

# 존재하지 않는 상품을 물으면 뭐라고 하는지
.venv\Scripts\python.exe scripts\explore.py entity "KODEX AI로봇"

# LLM에게 넘어가기 직전의 사전분석 내용 그대로 보기
.venv\Scripts\python.exe scripts\explore.py pre "신용등급 AAAA인 채권 찾아줘"

    추천: 마지막 두 개를 꼭 돌려보세요. "존재하지 않는 것을 어떻게 판정하는가"가 이 시스템의 핵심이고, 답변불가 문항 배점이 걸린 부분입니다.

  4. API 키 넣기

    .env.example을 .env로 복사하고 키를 채웁니다. 둘 중 하나만 있으면 됩니다.

    # 대회 규정: 반드시 HyperCLOVA X
LLM_PROVIDER=clova
LLM_MODEL=HCX-005
CLOVA_API_KEY=nv-...        # CLOVA Studio 테스트앱/서비스앱 API 키
CLOVA_BASE_URL=https://clovastudio.stream.ntruss.com/v1/openai
LLM_MAX_TOKENS=4096         # function calling 은 1024 이상 필수

    키는 네이버클라우드 콘솔 → CLOVA Studio → 테스트앱/서비스앱에서 발급합니다. 주의: HCX-005는 function calling과 사고(reasoning) 모드를 동시에 켤 수 없습니다. 우리 코드는 function calling만 씁니다.

  5. 서버 켜기

    .venv\Scripts\python.exe scripts\warmup.py          # 선택: 다음 기동이 80초 빨라짐
.venv\Scripts\python.exe -m uvicorn finagent.api:app --port 8000 --app-dir src

    기동에 1분 30초~3분 걸립니다(색인·벡터·그래프를 메모리에 올리는 시간). 브라우저에서 http://127.0.0.1:8000/health를 열어 "status":"ok"가 보이면 준비 완료입니다.

  6. 질문 하나 던져보기

    브라우저 주소창에 그대로 붙여넣어도 됩니다.

    http://127.0.0.1:8000/answer?question_id=Q-001&question=현재 판매가능한 원화채권 중 AA- 이상 종목 알려줘

    답을 읽는 법 — answer만 보지 말고 나머지 두 필드를 꼭 같이 보세요.

    • think_trace — LLM이 무엇을 했는지. 몇 라운드를 돌았고 어떤 SQL을 실행했고 몇 초 걸렸는지가 순서대로 나옵니다. 답이 이상하면 여기서 원인을 찾습니다.
    • retrieved_context — 근거. 이 숫자가 어느 테이블 며칠자 데이터에서 나왔는지. 여기 없는 숫자가 answer에 있다면 그게 환각입니다.

  7. 정답 키로 채점하기 — 진짜 성능 확인

    서버를 켜둔 채 다른 터미널에서:

    # 정답 키만 먼저 확인 (서버·키 없이도 됨)
.venv\Scripts\python.exe scripts\eval_truth.py --compute

# 서버 답변을 정답과 대조해 채점
.venv\Scripts\python.exe scripts\eval_truth.py --base http://127.0.0.1:8000

# 상태·지연시간 점검용 33문항 (정답 대조 없음)
.venv\Scripts\python.exe scripts\eval_run.py --base http://127.0.0.1:8000

    eval_truth는 20문항 중 몇 개를 맞혔는지를 백분율로 출력합니다. 정답은 채점 시점에 데이터에서 다시 계산되므로 사람이 채점표를 관리할 필요가 없습니다.

    여기서 봐야 할 것: ① 정답률이 몇 %인가 ② 300초에 걸리는 문항이 있는가(있으면 미응답 처리) ③ 답변불가 5문항이 전부 "확인할 수 없음"으로 나오는가 ④ X 문항의 think_trace를 열어 HyperCLOVA X가 어디서 헤맸는가 — 도구를 아예 안 불렀다면 max_tokens를 먼저 의심하세요.
