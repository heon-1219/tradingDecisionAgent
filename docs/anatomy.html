As of 2026-09-06. Where things stand, what changed today, what has been measured and what is still open.

Where things stand

Data loading, indexing, the graph and the API contract are working, and we now have records of running real questions through HyperCLOVA X. What we did today was not to add new features but to find and fix the places where existing things had been quietly wrong. The 20% (source, README, ontology) and 40% (evaluation API) parts of the score are in shape; the remaining 40%, the technical proposal, is still an outline skeleton.

One thing to make clear up front: this document contains no accuracy figure. Today, while growing the evaluation set from 20 to 54 questions, we also fixed errors in the answer key itself, so earlier grading results are no longer valid, and the new set has not been run yet. Rather than write a number we don't have, we write that we don't have it.

What widened today — four coverage gains

In one line: constituents, which lived only inside the knowledge graph, have moved down into a SQLite table (etf_constituent, 22,599 rows · 1,162 domestic ETFs). The graph is now built from that table. With a single source, SQL and the graph cannot disagree, and we checked on five companies that they actually don't: Samsung Electronics 229/229 · Samsung Electronics Pref. 19/19 · EcoPro BM 42/42 · LG 26/26 · KT 48/48.

Along the way we found that the collector was throwing away the itemCode the source (Naver Finance) provides for every constituent. With only the name left, identity hung on a name alone. We restored it, and now 79% of rows carry a ticker code. The same went for managers. Instead of guessing from the fund-name prefix, we now derive the manager from what the organizer provides 100% populated: or_co_xtn_itt_cd (manager institution code). How each row was filled is recorded in the new column manager_source (name 17,660 / code 3,932 / NULL 2,084).

11 bugs fixed today

  1. Even after the store was rebuilt, the vector cache kept accepting the old matrix. As a result, every search_products call died on a matrix-dimension mismatch.
  2. KG.find returned the same node once per alias, so every relation count came out exactly doubled (ETFs holding Samsung Electronics 238→476, EcoPro BM 42→84). Because the evaluation answer key was computed with the same code, the doubled numbers were being graded as correct.
  3. graph_neighbors cut the neighbors off at 60 and then reported that cap as the total count.
  4. 677 constituent rows were attached to the wrong company (LG→Shinhan Financial Group, KT→SK Telecom, Hana Micron→Micron). The cause: a lenient alias matcher built to interpret what users type was reused as-is to load 15,911 rows. "lg" is a substring of "shinhanfinancialgroup".
  5. A property's domain pointed at a class that covers only part of the table. A latent bug with no symptoms yet, but the moment that property was materialized, 545 domestic ETNs would have been classified as ETFs.
  6. sql_query reported the 200-row cap as the total count. For a filter matching 15,837 rows, it answered "200 in total".
  7. The model got numbers wrong while copying them from tool output. It wrote 240 as "24", and 25,474,813,891,225 once as "254조 4,818십억" (254 trillion 4,818 billion) and on the next run as "25조 4,748십억" (25 trillion 4,748 billion).
  8. _unit_warning threw an exception on the COUNT(*) + GROUP BY combination. Of all things, the "fund family summary" pattern the prompt teaches as an example has exactly that shape.
  9. has_buy_yield was listed in the prompt's column list but had no ontology definition, so it never once appeared in the schema card. The model did not know the column existed.
  10. The evaluation set itself had errors too. G-006's answer key counted ETNs in a question asking about ETFs; the grader did not recognize "…there are no such products" as a refusal; G-007 had a four-way tie at a 0.01% total expense ratio, yet only one answer was pinned as correct; and check:"number" accepted rounded integers, so a question whose answer is 0.65 passed as long as "1" appeared.
  11. When pandas Series.map returns None, it becomes NaN, and NaN is truthy. So the filling step did nothing and reported success. No exception, no log, tests passing.

If you take away just one thing, take this

All eleven of the above failed without looking like failures. No exception, no red test, no error left in a log. The doubled relation counts were confirmed as correct by an answer key built with the same code, the filling step that did nothing reported success, and a count cut off at a cap came out wearing the name "total".

So these were found not by running code, but by recounting results after making changes. In this project, "the tests pass" and "the numbers are right" are two different stories. After you fix something, count the same answer once more by a different path — values from SQL through the graph, values from the graph through SQL.

Decided and closed

  • HyperCLOVA X is mandatory. And CLOVA Studio cannot use tuning and function calling at the same time. This agent is one big function-calling loop, so the agent itself cannot be tuned. We did build 4,779 rows of training data for the tool-free text→text parts, but did not apply it.
  • A constituent's identity comes only from the ticker code the source provides. We do not link by name similarity — #4 above is what happened when we did.
  • We do not widen subsidiaryOf. The organizer's four masters have no ownership relations at all, and this project's rule is to compute from the provided data. So it stays at 4 edges, and we revised the docs so they do not imply more.
  • We do not build a manager-rename mapping from outside sources. Without fund inception dates there is no way to decide which of two names is the current one. So we use the majority spelling attached to the institution code — even when it is an old brand name.
  • "How many funds" means the number of distinct funds by fund_family, not the number of class rows (23,676 rows = 17,795 funds).
  • We expose all provided columns rather than choosing among them. The reason is simple — the model never calls table_info, not even once (tool-usage chart in section 7).

2. What we built

In one sentence: a server where you put a question in the address bar and get the answer back as JSON.

This is how evaluators query our server. No authentication, no POST. An address is all it takes. 

# What the evaluator sends ("show me KRW bonds currently available for sale rated AA- or higher")
GET /answer?question_id=Q-001&question=현재 판매가능한 원화채권 중 AA- 이상 종목 알려줘

Our server always returns 200 OK with exactly 5 fields. Even on errors, it never returns 500.

{
  "question_id": "Q-001",
  "question":    "…same as the request…",
  "retrieved_context": "[Evidence 1] 국내채권마스터 (v_bond_kr) · as of 2026-08-21 · 15,837 rows …",
  "think_trace":      "1. Pre-analysis … 2. Round 1: sql_query … 3. final_answer",
  "answer":           "구매 가능한 AA- 이상 원화채권은 15,837건입니다 …"
}

The key point is that evidence is always attached next to the answer. Which table and which date's data it looked at, how many rows, which SQL it ran and which product codes it referenced all stay in retrieved_context as-is. When the data cannot confirm something, it does not make things up; it answers "This cannot be confirmed from the provided data".

Why that matters — 5 of the competition's 35 evaluation questions are questions that cannot be answered. Producing a plausible answer to them loses points; saying "cannot be confirmed" is what gets graded as correct. In other words, in this system "the ability to say it doesn't know" is not an add-on feature but a scoring item.

4. How a single question is processed

The LLM doesn't "know" the answer; it uses tools to "fetch" it.

  1. Pre-analysis — before calling the LLM

    It pulls out the parts of the question that look like product names and checks them against real products, matches the company, theme and manager lexicons, and asks the ontology whether values like "AA-" or "risk grade 2" actually exist.

    # "신용등급 AAAA인 채권 찾아줘" ("find bonds rated AAAA") → the conclusion is reached before the LLM is even called
⚠ Ontology violation: credit rating 'AAAA' is not an existing value.
   Valid credit ratings: AAA, AA+, AA0, AA-, A+, … D

  2. The LLM makes a plan

    Given the question and the pre-analysis result, the LLM decides "this is a SQL problem" or "this needs the graph" and calls tools. We do not write the SQL in advance; the LLM writes it on the spot.

  3. Tools run and evidence is recorded

    Several tools run at the same time. Each result is automatically tagged with which table, which date, how many rows and what query, and together they become the final retrieved_context. This is the part that lets a human verify the answer.

  4. Repeat 2–3 (up to 8 rounds, 120 seconds)

    If the results fall short, it changes the conditions and searches again. When the 120-second budget is about to run out, the server tells it to "answer now with the evidence gathered so far". The organizer treats anything over 300 seconds as no response, so we set the budget to finish well before that. However, 17 of 22 questions waste one round writing prose without tools before submitting (section 7).

  5. The answer is submitted in one of 3 states

    answered (evidence found) · cannot_confirm (cannot be confirmed from the data) · clarify (conditions are ambiguous, so it asks back). If the LLM breaks the rules, the server corrects it at the end.

5. Store layout and ERD

Why the same data is indexed five different ways, and what the relational store actually looks like.

The shape of the relational store — 5 views

With constituents moving into SQLite today, this store got its first real foreign key. The other four views do not join with one another — different product groups share no common key — so cross-product queries are solved with UNION ALL rather than joins.

What the knowledge graph is made of

The hard sample question "에코프로의 자회사를 편입한 ETF 중 순자산이 큰 상품의 위험요인" ("risk factors of the largest ETFs by net assets among those holding EcoPro's subsidiaries") uses all three paths: find the subsidiaries in the graph → find the 43 domestic ETFs that hold them → sort by net assets with SQL → explain the risk factors from the documents. With SQL alone, even the first step is impossible. The organizer's data has no "constituents" column at all.

However, there are only 4 subsidiary edges. The organizer's four masters have no ownership relations at all, and this project's rule is compute from the provided data, so subsidiaryOf stays at 4: 3 in the EcoPro group plus 1 for SK Innovation. Presenting "multi-level subsidiary traversal" as a strength of this system would be an exaggeration. What works is the EcoPro group, and it works because we wrote those relations in by hand.

6. Forks and choices

What could be chosen at each step, what we chose, and why.

Decision 01

What overall structure to use

How much freedom should the LLM get?

RejectedOne-shot NL2SQLThe LLM writes one line of SQL and that's it. Fastest and simplest, but it can't handle theme, constituent or relation questions, and it produces answers even to unanswerable questions.
ChosenTool-using AgentThe LLM reads the situation and repeatedly picks among SQL, graph and search. Flexible, but response time and cost go up → controlled with a time budget.
RejectedFixed pipelineClassify the question and run a fixed template. The most predictable timing, but it collapses on 'hard' questions and is hard to extend.

Why — The evaluation questions mix 10 each of hard, medium and easy, plus 5 unanswerable ones. Looking only at the 'easy' questions, NL2SQL wins, but the 'hard' questions — a third of the score — can only be solved by moving across several stores. Instead, we built the fixed pipeline's strengths (time control, validators, forced termination) into the Agent as rules.

Decision 02

Where to put the data

In what form should the 8 Excel files be handled?

RejectedRead the Excel files every timeNo preparation needed, but every question takes tens of seconds, and filtering and sorting have to be hand-coded.
ChosenOne SQLite file53K rows is tiny for SQLite. No server to install, and as a single file it can be baked straight into the Docker image.
RejectedPostgreSQLCapable enough, but running a separate DB server for data this size only adds deployment and operations burden.

Why — The server has to stay up throughout the evaluation period (9/7–9/20). The fewer the moving parts, the less it dies. With SQLite, one container does it.

A bonus — We kept the original column names (pd_no, crd_grd) as they are, but computed columns with clear meanings and layered them on top as views. E.g. is_sellable (21,866 purchasable bond rows), fund_family (a key that groups the classes of the same fund — 23,676 rows collapse into 17,795 funds), manager_name (unified manager spelling).

Decision 03

How to use the ontology

It is a mandatory deliverable — should it exist only for the submission, or actually run?

RejectedSubmission document onlyProduce the TTL files but don't use them in code. Fills the 20% item, but contributes zero to answer quality.
RejectedPaste into the promptPass the ontology content to the LLM as a description. Per the technical-session material, the improvement is only +2.4%p.
ChosenRead and executed by the runtimeAt server startup, parse the TTL and automatically generate the column-description table and value validators. +20%p on the same material.

Why — The organizer's technical session published its own experimental numbers: "Use the ontology for 'execution', not 'description' — prompt injection +2.4%p, runtime identification +20%p". In effect, it spelled out what the graders want to see.

Actual effect — The TTL defines the 20 credit grades in order, so the phrase "AA- or higher" is automatically converted to ('AAA','AA+','AA0','AA-'), and "AAAA" is judged to be a non-existent value before the LLM is called.

Decision 04

Should the graph include inference?

If we store only "KODEX 로봇액티브 is a domestic ETF", should the system be able to answer "Is it an ETF? Is it a financial product?"

RejectedAnswer only what is storedSimple and fast to implement. But the query ?p a fp:ETF returns 0 rows — queries the LLM would naturally write fail silently.
ChosenGrow facts with rulesAt startup, compute and store superclass inheritance, inverse relations and domain/range. Materialized at startup. The current graph has about 1.07M triples · 73 predicates.

Why — Technical session 01-4 is entirely about this topic ("axioms + logical rules = new facts; put in 2 and you get 5"). At first it was missing, so every superclass query returned 0 rows; we found it while re-reading the task description and filled it in. By optimizing to process only the predicates actually in use, we once cut graph build time sharply (150 s → 83 s at the time). Today constituents moved into a table and predicates dropped from 5,082 to 73, changing the graph's composition again, so the build time needs to be re-measured.

Decision 05

How to combine search

How should search by name and search by meaning be blended? — the problem we wrestled with longest

RejectedLexical search onlyBest when the spelling is exact. But the task description explicitly required Vector, and it is weak on questions worded differently.
RejectedVector search onlyWhen asked for an exact product name, it ranks some unrelated look-alike product first. Dangerous.
RejectedEqual-weight RRF fusionThe textbook method. When we actually wired it up, we hit an incident where an unrelated product that each retriever had ranked somewhere in the middle took first place.
ChosenLexical head + vector tailLexical search keeps the top slots, and the bottom 30% of slots go to products "found only by vectors". A structure that cannot be worse than lexical.

Why — RRF (Reciprocal Rank Fusion) pushes documents that both retrievers agree on to the top. But when we asked for "배터리 양극재 관련 상품" (battery cathode material products), an unrelated fund of funds landed mid-rank in both, and so took first place ahead of BNK 2차전지양극재, which lexical search had found exactly.

Why this is dangerous — If the top candidate is wrong, the LLM writes its answer based on it. A search-ranking error spreads straight into an answer error. So we chose to guarantee by structure that "hybrid can never be worse than lexical search".

What vectors still earn — Asked in English for "China semiconductor ETF", lexical search finds only English-named foreign ETFs, but vectors add domestic ETFs such as KODEX 미국반도체 in the tail slots.

Decision 06

What to build the vectors with

Use an embedding API, or build them locally?

RejectedCommercial embedding APIThe best quality, but one more API key has to stay alive through the evaluation period, and embedding 53K items costs money and time.
RejectedLocal embedding modelNo key needed, but a 2 GB model download + CPU inference slows startup considerably and makes the image heavy.
ChosenTF-IDF + LSA (384 dims)Works deterministically with no key and is built in 13 seconds at startup. One environment-variable line switches to commercial embeddings.

Why — The evaluation API has to stay up for two weeks, and every extra external dependency raises the chance of it dying. In case quality falls short, we left the door open to switch with VECTOR_BACKEND=openai without code changes.

Fixed by measuring — The first vectors we built were useless. Asked for "배터리 양극재" (battery cathode materials), an unrelated private ELS fund came first with a similarity of 0.89. The cause: Korean product names are full of shell words like 증권투자신탁·사모·파생형 (securities investment trust · private · derivative-type), which pulled the vector space toward them. Cutting frequent words (max_df=0.005) raised the correct probes from 1 of 7 to 6.

Decision 07

Should we use external data?

Should we collect "ETF constituents", which the provided data lacks, ourselves?

RejectedProvided data onlyThe safest, with zero risk of breaking the rules. But 2 of the 5 sample questions cannot be solved at all.
ChosenCollect constituents + build lexiconsCollected the top holdings of 1,162 domestic ETFs (22,599 rows). A company lexicon links parent–subsidiary relations.

Why — The rules explicitly allow external collection ("participating teams may collect and use financial-product-related data"), and even warned that "questions will not ask only about the reference data". The sample questions "캠브리콘이 편입된 중국반도체 ETF" (China semiconductor ETFs holding Cambricon) and "에코프로 자회사를 편입한 ETF" (ETFs holding EcoPro subsidiaries) are fundamentally impossible without constituents.

Discovery — Naver Finance writes Cambricon as "한무기" (the Korean reading of 寒武纪). It can only be found by linking through the ticker code 688256. That is why the company lexicon carries aliases like this.

Rule we kept — When external data conflicts with the organizer's data, the organizer's data wins. This is stated in the prompt.

Decision 08

How to enforce "I don't know"

How do we avoid losing points on the 5 unanswerable questions?

RejectedAsk nicely in the promptInstruct it: "If you don't know, say you don't know." LLMs often disobey.
Chosen3 states + server correctionForce the LLM to pick a state whenever it answers, and if pre-analysis caught a "non-existent value" but the LLM made up an answer anyway, the server turns it back into cannot-confirm.

Why — A prompt is a request; code is a guarantee. The unanswerable questions carry points, so they can't be left to a request.

Decision 09

Which LLM to use — settled by the rules

Organizer's notice: the answer-generation pipeline must use NCP HyperCLOVA X.

FixedHyperCLOVA X (HCX-005)Connected through CLOVA Studio's OpenAI-compatible endpoint. Handles every stage the rules cover (intent analysis, answer generation).
Dev onlyAnthropic / OpenAIKept in the code but not allowed for submission or evaluation. Used only to compare answer quality.
N/AAdditional paid LLMsThe organizer advised against paid LLMs. We use no LLM outside the answer path (vectors are computed locally too).

The adapter structure paid off — Because an earlier decision separated the providers so they could be swapped, reflecting this notice took just one added class + a changed default. The tool-calling format is the same as OpenAI's, so the conversation logic was reused as-is.

Two things to watch with CLOVA — ① function calling works only when max_tokens is 1024 or more (below that it never calls tools at all, which looks like "the model won't use tools" — the code raises it automatically). ② function calling cannot be turned on together with the reasoning or structured-output modes.

Settings — LLM_PROVIDER=clova, LLM_MODEL=HCX-005, and the CLOVA Studio key in CLOVA_API_KEY. The endpoint is https://clovastudio.stream.ntruss.com/v1/openai.

Decision 10

What counts as "purchasable" — a definition overturned by a notice

Organizer's notice: BUYABLE_QUANTITY values are invalid; every issue except delisted or listing-ended ones is assumed purchasable.

DroppedHas a buy yieldAt first only bonds with a buy yield and a buyable quantity were treated as "available for sale" → 634.
CurrentNot yet redeemed = purchasableRedefined to match the notice → 21,866. Whether a buy yield is recorded is kept separately as has_buy_yield.

The impact is big — The answer to "purchasable KRW bonds rated AA- or higher" changes from 78 → 15,837. Had we missed this notice, we would have gotten every bond question wrong.

We rescued the information we lost — Buy yield and after-tax yield are still recorded for only 634 rows. So the prompt says explicitly that queries asking about "yield" must also apply has_buy_yield=1. Otherwise the result is a table whose yield columns are all empty.

Partly verified

(section 1, #7 — it once wrote 240 as "24") ③ does any question hit 300 seconds?

Data expansion

Constituent coverage may need widening for cross-product queries

The organizer's example of a cross-product query is "삼성전자를 보유한 국내/해외ETF와 공모펀드를 1년 수익률 기준 TOP10" ("top 10 domestic/foreign ETFs and public funds holding Samsung Electronics, by 1-year return"). The notice also says "which data to use for constituents–products and the like is up to you".

→ A decision to make depending on the time left. Adding foreign ETF constituents (e.g. each manager's disclosure PDF/CSV) or fund asset composition would widen cross-product coverage, but time until the September 6 freeze is tight. Priority: after HyperCLOVA X verification.

Schedule trap

Today is code-freeze day (9/6) — the API runs 9/7–9/20

Rules: "Disqualification if any change to code or deliverables after the deadline is discovered". Yet the API has to stay up from September 7 to 20. In other words, even if answers look wrong during the evaluation, we can't fix them.

→ Three items remain: grading on the 54 questions · the technical proposal body · attaching the remote repository and deploying. All of them must be done before 23:59 on September 6.

Settled

The LLM is settled: NCP HyperCLOVA X is mandatory

Notice: "NCP Hyper ClovaX is mandatory when building the API that produces answers to questions. Apart from query intent analysis - (data retrieval and evidence building) - answer generation, there are no restrictions." It came together with the advice "avoid using paid versions of LLMs".

→ We switched the default provider to clova/HCX-005. Data retrieval, search, graph and vectors are all code, not LLMs, so the rule doesn't touch them, and no paid LLM is used anywhere. One thing needs confirming: whether even "intent analysis" has to be HyperCLOVA X — but in our architecture HyperCLOVA X does both intent analysis and answer generation, so either interpretation satisfies the rule.

Room to tune

The response-time rule changed, so we raised the budget

Notice: "The response-time criteria are not disclosed; the 300-second timeout is a physical 'no response' cutoff, and late responses (under 300 seconds) will be scored differently." In other words, being slow but right beats being fast but wrong.

→ We raised the internal budget from 50 s → 120 s and the tool rounds from 6 → 8. This needs readjusting after measuring HyperCLOVA X's actual response speed. Any question that hits 300 seconds counts as no response, so that must be avoided at all costs.

Data limits

You need to know which data is missing

Domestic ETF total expense ratio is populated for only 18%, the fund fee columns have no disclosed unit (no absolute interpretation; relative comparison between classes only), and foreign ETFs and funds have no constituents. Besides the 14,716 public funds, the fund master also mixes in 8,960 private funds.

→ All of this is written into the prompt and the ontology annotations, and the system answers "no data" when a value is missing. When reviewing answers, please check that this is honored.

Base date

Constituents have a different as-of date from the product data

The product masters are as of 2026-08-21 (foreign ETFs 08-22), but the constituent table (etf_constituent) has as_of 2026-09-05.

→ When answers mix the two, keep in mind that the dates differ. Re-collecting once right before submission would narrow the gap.

Submission format

The repository's top-level structure has to match

The structure the task description requires is src/, ontology/, requirements.txt and README.md at the repository root. Right now they are in the fin-agent/ folder — inside it, not at the root.

→ When uploading to the organizer's repository, the root must hold fin-agent/'s contents, not the folder itself. The submission must also include the API address and the specification.

9. Try it yourself

Just follow along in order. Steps 1–3 work without an API key.

  1. Set up the environment (once)

    In a Windows terminal, go to the fin-agent folder, then:

    # The virtual environment already exists in .venv
.venv\Scripts\python.exe -m pip install -r requirements.txt

# Build the database (1–2 min) — skip this if it already exists
.venv\Scripts\python.exe scripts\build_store.py

    Success signal: done: {'bond_kr': 21882, ... 'fund_pub': 23676} is printed and data/store/products.db is created.

  2. Run the tests — full verification without a key

    .venv\Scripts\python.exe -m pytest -q

    Success signal: 52 passed. If something fails, the file name tells you which part broke (test_build_store=data loading, test_graph=graph and inference, test_vector=vector search, test_agent=API contract).

  3. Look inside directly — this is where it clicks

    We built a tool that puts questions to each store directly, without the LLM. Running it a few times is the fastest way to understand the system.

    # What's loaded right now, at a glance
.venv\Scripts\python.exe scripts\explore.py health

# Run SQL directly — the same views the LLM uses
.venv\Scripts\python.exe scripts\explore.py sql "SELECT pd_nm, crd_grd, buy_yield FROM v_bond_kr WHERE is_sellable=1 ORDER BY buy_yield DESC LIMIT 5"

# Compare the 3 search modes — see Decision 05 for yourself ("차이나 반도체" = "China semiconductor")
.venv\Scripts\python.exe scripts\explore.py search "차이나 반도체" --mode lexical
.venv\Scripts\python.exe scripts\explore.py search "차이나 반도체" --mode vector
.venv\Scripts\python.exe scripts\explore.py search "차이나 반도체" --mode hybrid

# Graph relations — what are EcoPro's subsidiaries?
.venv\Scripts\python.exe scripts\explore.py graph "에코프로" --relation hasSubsidiary

# What it says when you ask about a product that doesn't exist
.venv\Scripts\python.exe scripts\explore.py entity "KODEX AI로봇"

# See the pre-analysis exactly as it is handed to the LLM ("find bonds rated AAAA")
.venv\Scripts\python.exe scripts\explore.py pre "신용등급 AAAA인 채권 찾아줘"

    Recommended: be sure to run the last two. "How it decides that something doesn't exist" is the core of this system, and it is where the points for unanswerable questions are at stake.

  4. Add the API key

    Copy .env.example to .env and fill in the key. You only need one of the two.

    # Competition rule: HyperCLOVA X is required
LLM_PROVIDER=clova
LLM_MODEL=HCX-005
CLOVA_API_KEY=nv-...        # CLOVA Studio test-app/service-app API key
CLOVA_BASE_URL=https://clovastudio.stream.ntruss.com/v1/openai
LLM_MAX_TOKENS=4096         # function calling requires 1024 or more

    Issue the key in the NAVER Cloud console → CLOVA Studio → test app/service app. Note: HCX-005 cannot turn on function calling and reasoning mode at the same time. Our code uses only function calling.

  5. Start the server

    .venv\Scripts\python.exe scripts\warmup.py          # optional: makes the next startup 80 s faster
.venv\Scripts\python.exe -m uvicorn finagent.api:app --port 8000 --app-dir src

    Startup takes 1 min 30 s to 3 min (the time to load the index, vectors and graph into memory). In a browser, open http://127.0.0.1:8000/health; once you see "status":"ok", it's ready.

  6. Ask it a question

    You can also paste this straight into the browser's address bar.

    http://127.0.0.1:8000/answer?question_id=Q-001&question=현재 판매가능한 원화채권 중 AA- 이상 종목 알려줘

    How to read the answer — don't look only at answer; always look at the other two fields as well.

    • think_trace — what the LLM did. How many rounds it ran, which SQL it executed and how many seconds it took, in order. If an answer looks off, this is where you find the cause.
    • retrieved_context — the evidence. Which table and which date's data each number came from. If the answer contains a number that isn't here, that's a hallucination.

  7. Grade with the answer key — check real performance

    With the server running, in another terminal:

    # Check just the answer key first (works without the server or a key)
.venv\Scripts\python.exe scripts\eval_truth.py --compute

# Grade the server's answers against the key
.venv\Scripts\python.exe scripts\eval_truth.py --base http://127.0.0.1:8000

# 33 questions for status/latency checks (no answer comparison)
.venv\Scripts\python.exe scripts\eval_run.py --base http://127.0.0.1:8000

    eval_truth prints how many of the 54 questions it got right as a percentage. The answers are recomputed from the data at grading time, so nobody has to maintain a scoring sheet by hand.

    What to look at here: ① what the accuracy % is ② whether any question hits 300 seconds (if so, it counts as no response) ③ whether all 5 unanswerable questions come out as "cannot be confirmed" ④ open the think_trace of the X questions to see where HyperCLOVA X got lost — if it never called a tool at all, suspect max_tokens first.
