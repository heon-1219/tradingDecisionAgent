Three things to read first

①What we built. A federated retrieval agent in which a single question splits into five paths — RDB · knowledge graph · lexical index · vector index · document store — and merges back into one answer. Because all five paths reference one and the same ontology, they can verify each other’s answers.

②What is different. We use the ontology as an execution layer that generates schema cards and value validators at startup. And we made it standard procedure to recount the numbers produced by SQL through the graph and compare the two.

③What we measured. Accuracy 47/54, average 20.6 s, net contribution of the vector leg +3.5 pp, marginal cost of an extra round +11.2 s. All of these are measured values. We report unfavorable results as they are, including the fact that the vector leg contributes little (06-D).

01Problem Definition

On the surface, the task looks like an NL2SQL problem: four structured master datasets are given, and natural-language questions must be answered. But once you actually open the data, “a row is not a product,” “the relationship the question asks about does not exist in the data at all,” “different kinds (species) are mixed within one table,” and “blanks are intended values.” None of these four is solved by writing SQL well. What is needed first is an agreed definition of what is being counted.

01-2. The hardest difficulty — there is no way to check the right answer

The organizers do not disclose the evaluation questions or their answers (task description: no reference question set included). So we have to build the answer key ourselves. And therein lies a trap. If the answer key is computed with the same code as the system, then whenever the code is wrong, the answer and the key are wrong together — and grading shows green.

That actually happened. The knowledge graph had inflated the number of constituent relationships twofold, and it was still the “right answer” — because the answer key had been computed with the same code as the graph. After this incident, we made it standard procedure to recount the numbers produced by SQL through the graph, and the numbers produced by the graph through SQL, and compare them (02-3, 05-1).

“After you change something, count the results again.”

None of the six incidents above threw an exception, left a log entry or turned a test red. They are not caught by looking at success or failure; they are caught only by counting again. So for every load and fill step we made it procedure to recompute and compare the record counts before and after the operation.

02Proposed Approach

This chapter answers, in order, the three questions set by the organizers — ① what specialized data did we collect and cleanse, and how, ② what ontology engineering did we apply, and ③ which retrieval methodology did we choose, and why did we design it that way.

02-1. What specialized data did we collect and cleanse, and how

Principle — external collection only for “items with no column at all in the provided data”

The rule is compute it from the provided data. External collection is not an exception to that rule: it was applied to only one item that cannot be computed because the provided data has no column for it at all (ETF constituents). Whether the rule was actually kept can be checked from the provenance breakdown of the knowledge graph.

How to catch silent errors

One fill step in the pipeline was reporting success while filling no rows at all: when pandas’ Series.map returned None, it became NaN, and NaN is truthy. There was no exception, no log entry, and the tests were green. So every fill step now looks not at success or failure, but at the number of rows filled before and after the operation.

What we chose not to fill — if the evidence is not in the provided data, we do not fill it in

  • A manager-rename mapping table: old and new brands are observed together under one institution code, but the provided data has no fund inception date, so there is no basis for deciding which is the current name. Pulling in an external table would break the rule, so we use the majority spelling as is — even when it is the old brand.
  • Domestic ETF TER (18% populated) · fund returns (about 30% populated) · fund fee units: these are values the source did not provide. We do not estimate them and answer “no data”; because the unit of the fund fee columns is undisclosed, we allow only relative comparisons between classes.
  • Return outliers: some 1-year returns exceed 200%, but since these are values supplied by the organizers, we use them as is, unmodified.

External collection — constituents, and the affiliates derived from them

We collected the top constituents of 1,162 of the 1,235 domestic ETFs (22,599 rows), loaded them into the SQLite table etf_constituent, and generated the knowledge graph’s hasConstituent from that table. Because both paths read the same source, SQL results and graph results do not diverge.

From there we derived affiliate relationships. The constituents of group-stock ETFs (TIGER 삼성그룹 [Samsung Group], PLUS 한화그룹주 [Hanwha Group stocks], etc.) are precisely the member companies of that business group, so we materialized them as affiliateOf — 608 edges across 65 companies in 8 groups, with 0 false positives (derive_group_affiliates in kb/graph.py). This, however, is the fact of belonging to “the same business group,” not “equity ownership.” The data has no shareholding ratios, so the levels cannot be told apart, and answers therefore also say “affiliate.” The hand-written subsidiaryOf consists of just 4 edges, and we do not claim “multi-level subsidiary traversal” as a general capability.

02-2. What ontology engineering did we apply

Six TTL files are read at startup to automatically generate ① the schema card shown to the LLM, ② the validator that filters the values in a question, and ③ the inference rules materialized into the graph. As a result, the cost of adding a new product type drops to one view + one TTL.

A limitation we want to state — the 13 SHACL NodeShapes are declared, but runtime validation is not applied (pyshacl is not among the dependencies). For now, SHACL serves as a specification of the constraints; the actual blocking of values is done in the pre-analysis stage by the validator generated from the ontology’s enumerations. Adopting pyshacl is left as an extension item (05-3).

02-3. Which retrieval methodology did we choose, and why did we design it that way

Five paths — but which ones to switch on is decided deterministically

Different elements of a query take different paths — numeric filters, sorting and aggregation go to SQL; relationship traversal to the graph; name and description matching to BM25; background knowledge to the documents. We did not leave this choice to the model. Before the LLM is called, pre-analysis draws up a retrieval execution plan, runs in advance only the stores the question needs, and injects the resulting rows into the first prompt as facts (plan_retrieval in agent/routing.py).

Hybrid fusion — why we dropped RRF, and how large the alternative’s gain measured

At first we fused BM25 and vector results on an equal footing with RRF (Reciprocal Rank Fusion). RRF lifts documents on which both retrievers agree, but in this corpus we saw cases where unrelated funds that each retriever had placed mid-list pushed out the top lexical match (“products related to battery cathode materials” → rank 1 was an unrelated fund of funds). If the top candidate is wrong, answer generation is contaminated, so the final structure is: lexical results take the head of the list, and the bottom ~30% of the slots are reserved for documents “found only by semantic search.”

The model does not ask about the schema — so we changed the prompt design

In the 54-question run, the tools the model actually called were sql_query 49 times, graph_neighbors 7 times and search_products twice; search_documents, table_info and graph_query were called 0 times each. The model does not ask about the schema. Therefore a column that is not in the prompt from the start effectively does not exist for the model. In fact, has_buy_yield was in the column list but had no ontology definition, so it did not appear on the schema card — and the model never used that column. This is why we decided to expose all 215 provided columns rather than a curated selection, and the measurement showing that latency does not grow even when the prompt grows 22-fold (05-2) backs that decision.

“What was handed over as fact at the moment of use was followed (5/5); prompt rules given in advance were ignored (4/4).”

Repeated measurements gave the same result. Adding more warnings had no effect; handing the model the schema card, the pre-retrieved results and the lookup keys at the very moment it uses them did.

The clearest case: in a cross-product query, the warning “foreign ETFs have no 1-year return, so exclude them” was ignored, but once we removed foreign ETFs from the UNION in the example SQL, that failure disappeared — the warning was not read, while the example was copied. So instead of adding rules, we provide examples and facts in which the rules are already reflected.

Answer generation — answers without a lookup are refused

When the model answers without calling tools, it makes up products that do not exist (Table 2). So final_answer enforces three states — answered / cannot_confirm / clarify — through the tool schema, and the server rejects and sends back any submission made without a single lookup. In the 54-question run this guard fired 5 times.

05-4. Scalability — the cost of adding a new product type

Directions for extension

  • More product types — overseas bonds · wrap accounts · trusts · derivative-linked securities (ELS/DLS) each attach as one view + one TTL. The procedure has already been validated on the four masters.
  • More relationships — affiliateOf currently consists of 608 edges derived from group-stock ETFs. If shareholding data becomes available, the same pipeline can formally derive subsidiaryOf, promoting “affiliate” to “subsidiary.”
  • Better retrieval — switch to commercial embeddings with VECTOR_BACKEND=openai (no code change needed). This leaves room to exceed the current TF-IDF+LSA ceiling, but we do not claim an improvement we have not measured.
  • Stronger validation — adopt pyshacl so the 13 SHACL NodeShapes, so far only declared, are validated at load time.
  • Sharper definitions — declare “what counts as one”, the cause of 4 of the 7 wrong answers, as explicit cardinality in the ontology (05-1, Table 8).

Basis of the accuracy figuresBecause the organizers did not disclose the evaluation set, the figures are based on 54 self-built questions. They are not performance on the organizers’ evaluation set.
Ambiguous definition of “how many”One fund row = one class, and a bond has several LOT rows per issue. Whether “how many funds” means the number of classes or of families is decided by definition, not by the data. 4 of the 7 wrong answers stem from this (Table 8).
Net contribution of the vector legLimited to +3.5 pp recall@10 on thematic queries (87.0 → 90.5). recall@1 · @5 are identical to lexical alone, and typo tolerance comes from the BM25 Hangul bigrams (93.1%), not from the vector index (45.0%). It exists and works as a required component, but in this corpus the range in which semantic search beats lexical search is narrow.
Affiliate ≠ subsidiaryThe 608 affiliateOf edges derived from group-stock ETFs (8 groups, 65 companies, 0 false positives) record membership of the same business group, not equity ownership. The data has no shareholding ratios, so the levels cannot be told apart, and answers therefore also say “affiliate.” The hand-written subsidiaryOf consists of just 4 edges, and we do not claim “multi-level subsidiary traversal” as a general capability. Unlisted affiliates are invisible, and only 2 Hyundai Motor Group companies are captured (the matching tokens were kept narrow to avoid false positives). SK Group is not covered because its ETF has no constituent rows.
SHACL not validated at runtimeThe 13 NodeShapes are declared, but because pyshacl is not a dependency, no actual validation is performed at load time. Value blocking is handled in the pre-analysis stage by the validator generated from the ontology’s enumerations.
Constituent coverageConstituents exist only for domestic ETFs (collected for 1,162 of 1,235). There are no constituent data for foreign ETFs or public funds, and such questions are answered as unverifiable. Also, only the top holdings are included, so this is not a complete holdings list (the cause of wrong answer G-037).
Reference-date mismatchThe constituents’ as_of is 2026-09-05, while the product masters are as of 2026-08-21 (foreign ETFs 08-22). When an answer mixes the two sources, the difference in timing is stated as well.
Low-coverage columnsOnly 18% of domestic ETF TERs and about 30% of fund returns are populated. The unit of the fund fee columns is undisclosed, so only relative comparisons between classes are allowed. Foreign ETFs have no 1-year return, so they are excluded from cross-product comparisons, and the answer says so.
Missing fund managers91.2% filled; 2,084 rows are still NULL. We built no manager-rename mapping table — without fund inception dates, there is no way to determine which spelling is the current name.
Size of the external documentsOnly 3 files, 39 chunks (ETF terms and metrics, general ETF risk factors, an overview of the National Growth Fund). They do not cover descriptive questions broadly, and questions that need background knowledge absent from the masters are answered as unverifiable.
Provided data vs. task descriptionThe task-description PDF states about 145,000 records across the four datasets with a reference date of 2026-07-11, but the files actually distributed total 53,375 records · reference date 2026-08-21. This implementation is based on the files actually provided; if the evaluation data is updated, re-running python scripts/build_store.py is all it takes to pick it up (assuming the same schema).
What we did not measureContainer startup time (needs re-measuring after the constituents table was added and the graph rebuilt) · retrieval quality after switching to commercial embeddings · concurrent throughput (not measured, since the organizers specified sequential calls). Since we did not measure them, we give no figures.
